## Planned Coverage

**Core thesis:** The engineer who can write clearly has 10x the influence of the engineer who cannot. A design doc that nobody reads is the same as no design doc. Writing is not a soft skill — it is a force multiplier.

**Topics to cover:**

### Part 1: Why Technical Writing is an L6 Skill
- How writing scales your influence beyond your direct team
- The asymmetry: you write once, 50 people read it
- Why great engineers often write poorly (and why it costs them)
- The three audiences: your team, adjacent teams, future-you

### Part 2: The Design Document
- What a design doc is for (alignment, not approval)
- The 6-part structure: problem, goals/non-goals, design, alternatives, risks, timeline
- What goes in "alternatives considered" (and why skipping it loses credibility)
- The "10x question" in every design doc: what breaks if this gets 10x bigger?
- Bad design doc vs good design doc — same topic, shown side by side
- When NOT to write a design doc (small changes, already-decided things)

### Part 3: The RFC (Request for Comments)
- RFC vs Design Doc: RFCs invite broader input on open questions; design docs record decisions
- How to write an RFC that gets useful feedback (not silence, not chaos)
- Structuring the question so reviewers know what you need from them
- Setting a deadline and making a decision even with partial consensus

### Part 4: The ADR (Architecture Decision Record)
- What an ADR is: a permanent record of a decision and the context that led to it
- The 5-part ADR format: status, context, decision, consequences, alternatives
- Why ADRs are for future-you and future-teammates, not for current approval
- Where to store ADRs (in the repo, near the code they affect)

### Part 5: Post-Mortems (Writing, Not Just Filling a Template)
- The difference between a post-mortem that changes the system and one that satisfies a process
- How to write the timeline section (chronological, facts only, no editorializing)
- How to write root cause that is systemic, not individual
- How to write action items that are specific and verifiable
- The "5 whys" in writing: when it works and when it circles back

### Part 6: Runbooks
- Runbook vs wiki: a runbook is for 2 AM, a wiki is for daylight
- The anatomy of a useful runbook: symptom → check this → if X do Y, if Z do W
- How to write steps that work for someone who doesn't know the system
- Keeping runbooks alive: ownership, dates, testing

### Part 7: How to Write Clearly (The Craft)
- The one-sentence summary that every document must have
- Active vs passive voice in technical writing
- Tables over prose for comparisons
- The pyramid structure: conclusion first, evidence below
- What to cut: filler phrases, hedge words, meta-commentary
- Getting feedback: what to ask reviewers for

### Exercises
- Write a design doc for a fictional feature (given a problem statement)
- Take a bad design doc (provided) and rewrite the alternatives section
- Write a post-mortem for the fictional checkout incident from Chapter 73
- Write a runbook for diagnosing a service that is returning 503s
